# [File Dropzone] Demo sample reload button accessible name does not contain the visible text "Reload ..."

## Issue summary

Under the "Try Demo" tab panel, when a user selects a sample image (e.g., "Mountain Sunrise" or "Team Collaboration"), the visible label on the action button dynamically updates from "Load [Sample Name]" to "Reload Mountain Sunrise" or "Reload Team Collaboration" to communicate that the sample has already been populated in the workspace. However, the programmatic accessible name of the button defined by its `aria-label` attribute remains statically hardcoded to `"Load Mountain Sunrise demo image"` or `"Load Team Collaboration demo image"`.

This creates a critical barrier for users who rely on voice dictation and speech control software (such as Apple Voice Control, Dragon NaturallySpeaking, or Windows Voice Access). Under WCAG 2.2 Success Criterion 2.5.3 (Label in Name), when a user interface component includes visible text, its programmatic accessible name must contain the visible text (ideally positioned at the start of the accessible name). When a voice dictation user speaks the natural command *"Click Reload Mountain Sunrise"*, the speech engine searches the accessibility tree for a control matching "Reload Mountain Sunrise". Because the underlying accessible name starts with "Load" rather than "Reload", the voice recognition software fails to find or trigger the button. The user is forced to fall back to tedious workarounds such as activating visual grid overlays or mouse simulation.

### Expected

The `aria-label` attribute remains fixed to `"Load Mountain Sunrise demo image"` regardless of loaded state, while the visible button text changes to `"Reload Mountain Sunrise"`, failing speech recognition label-matching algorithms.

By relying solely on the child visible text content for accessible name computation, the accessible name is guaranteed to match the visible text in all application states. This eliminates any risk of attribute desynchronization, removes redundant ARIA markup, and ensures voice dictation software (Apple Voice Control, Dragon) flawlessly activates the buttons when users speak the visible text label.

# [Output Snippet] Card header in "Raw Alt Text Description" causes horizontal page overflow at 320px viewport width (400% zoom)

## Issue summary

When alt text is generated, the application presents the results in three card containers inside the "Generated Alt Text & Snippets" section (`OutputSnippet.jsx`). In the first card ("Raw Alt Text Description"), the header container is laid out using `flex items-center justify-between` without wrapping (`flex-wrap`). The left side contains an icon and the heading text "Raw Alt Text Description", while the right side contains two inline buttons: "Edit" and "Copy Text".

On a 320 CSS pixel viewport width (which models 400% zoom on a standard 1280px desktop monitor per WCAG 2.2 Success Criterion 1.4.10 Reflow), the combined minimum widths of the title (`180px`), action buttons (`161px`), and enclosing card/container padding (`72px`) total over `340px`. Because the flex container does not allow wrapping, the buttons push beyond the right edge of the screen, extending the document body scroll width to `330px`. This triggers bidirectional horizontal and vertical scrolling across the entire web page.

Low-vision users who rely on screen magnification and browser zoom up to 400% are severely impeded. They must continually pan horizontally back and forth to read sentences and interact with controls, causing extreme cognitive strain and physical fatigue.

# [File Dropzone] Custom file upload dropzone interactive button contains a child `<h3>` heading element

## Issue summary

In the "Upload File" tab panel (`FileDropzone.jsx`), the custom drag-and-drop file upload trigger is implemented as a focusable `<div>` element with `role="button"` and `tabIndex={0}`. Nested inside this interactive button element is a semantic level 3 heading:
`<h3 className="block text-xl sm:text-2xl font-display font-bold text-ink dark:text-cream mb-2">Drag & Drop Image Here</h3>`.

According to the W3C HTML specification and WAI-ARIA Authoring Practices Guide (APG), interactive controls (including `<button>` and elements with `role="button"`) must not contain heading elements (`<h1>`–`<h6>` or `role="heading"`). Placing a heading inside a button produces conflicting semantics in the browser's accessibility tree:

- In Apple VoiceOver on macOS and iOS, the heading role is flattened and stripped from the Headings Rotor. Blind users who navigate web pages by cycling through headings never discover the "Drag & Drop Image Here" upload section.
- In NVDA and JAWS on Windows, pressing the heading navigation shortcut (`H`) jumps keyboard focus directly into the interactive button control itself. Screen readers announce "Heading Level 3 Drag & Drop Image Here button", confusing users who expect heading navigation to browse static content outlines rather than trigger file upload dialogs.

# [Output Snippet] Horizontally scrollable code snippet blocks (HTML and Markdown) are not keyboard focusable

## Issue summary

In the "Generated Alt Text & Snippets" section (`OutputSnippet.jsx`), the generated HTML image snippet (`<img src="..." alt="..." />`) and Markdown syntax (`![...](...)`) are rendered inside styled preformatted containers styled with Tailwind's `overflow-x-auto` class (`<div className="... overflow-x-auto ..."><code>...</code></div>`).

Because generated alt text descriptions are often 100 to 200 characters long, these code blocks frequently overflow horizontally, clipping the right side of the code. However, neither container specifies a `tabindex="0"` attribute, a `role="region"`, or an accessible label.

As a result, sighted keyboard-only users (who use `Tab` and `Shift + Tab` to navigate) and users of mouth sticks, head wands, or single-switch access devices cannot focus the scrollable code containers. When pressing `Tab`, the focus cursor jumps directly from the "Copy" button of one card to the next card, completely skipping the scrollable code container. Because the region cannot receive focus, keyboard users cannot use the `Left` and `Right` arrow keys to scroll horizontally and inspect the generated code.

# [File Dropzone] Activating demo load buttons causes triggering button to become disabled during async fetch, dropping keyboard focus to `<body>`

## Issue summary

In the "Try Demo" tab panel (`FileDropzone.jsx`), when a keyboard-only or screen reader user activates either the "Load Mountain Sunrise" or "Load Team Collaboration" button (`natureBtnRef` / `teamBtnRef`), `handleLoadSample` triggers an asynchronous `fetch` for the sample image blob. While the fetch request is in flight, the component sets `disabled={isLoading}` on both demo buttons.

In web browsers, applying `disabled` to an element that currently holds active keyboard focus immediately expels focus from the element and drops it to `document.body`.

Furthermore, while the upload and URL panels feature explicit `useEffect` hooks to move focus to the revealed preview card's Close button (`closeBtnRef.current?.focus()`), no such focus management exists for the Try Demo workflow. When the network request completes and the preview card appears:
- Focus remains stranded on `document.body`.
- Screen reader users are left disoriented with no audible feedback regarding where their focus is located.
- Pressing `Tab` causes sequential keyboard navigation to start over from the very top of the entire document (`Skip to main content` in `<header>`), forcing the user to tab through the entire page header and tablist again just to reach the loaded image preview.

Activating a demo sample retains focus on the triggering button or programmatically moves focus directly into the revealed preview card (such as its "Close" button), maintaining a logical, uninterrupted sequential keyboard flow.

Add a focus management `useEffect` in `FileDropzone.jsx` for the demo tab workflow matching the upload and URL workflows, moving focus to `closeBtnRef.current?.focus()` when `isDemoLoaded` transitions to `true`.     }, 0);
  }
  prevIsDemoLoadedRef.current = isDemoLoaded;
}, [isDemoLoaded, activeTab]);

# [Header] GitHub repository icon link opens in a new tab without programmatic indication

## Issue summary

In the application header (`Header.jsx`), the GitHub link icon renders as:
`<a href="https://github.com/svinkle/alt-text-generator" target="_blank" rel="noopener noreferrer" aria-label="GitHub repository">`.
The link has `target="_blank"` and opens the repository in a new browser window or tab. However, the accessible name defined by `aria-label` is strictly `"GitHub repository"`, providing no programmatic announcement or visual cue that activating the link will open an external tab.

Similarly, in the footer (`App.jsx` line 403), the external guidelines link:
`<a href="https://www.w3.org/WAI/tutorials/images/decision-tree/" target="_blank" rel="noopener noreferrer">W3C Image Decision Tree Guidelines ↗</a>`
relies solely on a unicode north-east arrow character (`↗`), which screen readers announce literally as "north east arrow" rather than an indication of link target behavior.

When screen reader users or users with cognitive disabilities activate these links, a new tab or window opens without warning. Users who subsequently press the browser's "Back" button find that the button is disabled because a new browsing context has been created, causing confusion, lost orientation, and accidental navigation disruptions.
